# SH 장애 분리와 알림 (2026-11-01)

## 구현 동작

1. 청약홈·LH의 정상 수집 결과를 생성합니다.
2. SH 수집과 SH 데이터 검증을 별도 오류 경계로 실행합니다.
3. SH 성공이면 새 SH 결과를 사용하고 출처별 성공 시각을 기록합니다.
4. SH 실패면 이전 공개 `calendar.ics`의 DESCRIPTION이 `SH 공식 홈페이지 자동 수집 /`으로 시작하는 VEVENT만 검증 후 보존합니다. URL·UID·시작/종료일을 검증하고 다른 출처 일정은 복사하지 않습니다.
5. 전체 안내 페이지에 SH 경고 배너를 표시하고 `status.json.sources.sh.state=stale`, SH 마지막 성공/시도 시각, 보존 건수를 기록합니다.
6. 캘린더 업로드와 Pages 배포를 완료한 뒤 새 SH 실패를 감지한 경우에만 별도 알림 job을 실패시킵니다. GitHub 계정의 실패 알림 설정을 사용하며 새로운 이메일 인증정보를 저장하지 않습니다.

설치 단계도 `continue-on-error`로 처리하므로 Chromium 준비 실패가 청약홈·LH 실행 자체를 막지 않습니다. SH 기능을 끄거나 다른 출처 수집이 실패하는 경우는 기존 정책을 유지합니다.

## 알림 빈도

이전 공개 상태 파일과 비교하여 최초 실패, 회복 뒤 재실패, 오류 원인 변경만 새 실패 알림으로 남깁니다. 동일 오류가 반복되면 경고 배너는 유지하지만 같은 실패 알림을 반복하지 않습니다. 회복은 안내 페이지/상태 파일에 반영하며 별도 회복 이메일은 보내지 않습니다.

## 백업을 읽지 못하는 경우

이전 일정까지 복구하지 못하면 SH 일정을 지우는 새 캘린더를 배포하지 않고 전체 배포를 중단합니다. 이는 마지막 공개본을 보호하는 예외입니다. GitHub Pages 주소 변경/전체 네트워크 장애에서도 무조건 다른 출처만 배포한다고 보장하지 않습니다.

이전 버전의 상태 파일에 출처별 상태가 없어도 전체 배포의 성공 시각을 초기 SH 성공 시각으로 사용하여 기존 8개 SH 일정을 보존할 수 있음을 현재 운영 파일로 확인했습니다.

## 검증

오프라인 테스트 51개 통과. SH 오류/누락 브라우저 의존성/잘못된 날짜 데이터, 이전 SH UID·내용 보존, 다른 출처와 병합, 최초 버전 전환, 연속 실패 시 시각 유지와 중복 알림 억제, 회복, 이전 파일 복구 실패 시 배포 차단을 검증했습니다.

GitHub 계정의 실제 이메일 수신은 사용자 개인 알림 설정에 의존하므로 별도 확인해야 합니다. 운영 파일을 일부러 망가뜨리거나 실제 오류 이메일을 강제로 발송하는 시험은 하지 않습니다.
